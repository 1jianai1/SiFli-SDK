## 1. 背景：这条链路长什么样（先建立概念）

```
应用 (demo main.c)
   │  调用 aic_wifi_demo_test()
   ▼
AIC 驱动的 platform 层（本仓库源码，可改）
   │  电源/GPIO、SDIO 寄存器读写封装、固件数组、任务/栈/优先级
   ▼
预编译 host 库 libaic8800_driver.a（不可改，只有符号）
   │  协议栈、固件下载流程、消息通道、与芯片对话
   ▼
RT-Thread SDIO / MMCSD 核心（SDK，非必要不改）
   │  寻卡(CMD0/5/3/7)、CCCR/FBR/CIS 解析、驱动匹配、CMD52/CMD53
   ▼
SiFli SDHCI 控制器驱动 drv_sdhci.c
   ▼
硬件：SDIO 4 线 + 芯片电源脚 GPIO124
```

三个必须分清的概念（后面所有讨论都依赖它们）：

1. **寻卡（枚举）**：主机发 CMD0/CMD5/CMD3/CMD7 并读 CIS，**完全不看厂商 ID**。失败现象 = 日志停在 `detect SDIO begin`。
2. **驱动匹配**：拿卡上的 VID/PID 与驱动 ID 表比对，成功才调用 `probe`。失败现象 = 有 `card registered` 但没有 probe 打印，`sdio_register_driver` 返回 `-RT_EEMPTY(-4)`。
3. **固件下载**：AIC8800 是"无片上固件"芯片，**每次上电都要由主机把固件通过 SDIO 灌进去**（CINIT → patch → fmac → 启动）。这一段必然产生 **CMD53 块传输**——**没有 CMD53 = 固件没下载**。

**芯片的启动阶段划分**（P6 就在这里）：

```
上电 → 芯片 bootrom 启动
      → 主机 SDIO 枚举 + func1 配置                       ✅ 已通过
      → 【bootrom 消息握手：主机给芯片发消息配置寄存器】    ❌ 卡在这里
      → 主机上传 CINIT / patch / fmac（CMD53）             ❌ 从未开始
      → 启动固件 → 固件与主机建立消息/数据通道
      → MAC 初始化 → netif → GetWiFiInitStat()==Ready
```

## 2. 问题清单（逐条：现象 / 证据 / 根因 / 修改）

### P1 —— SDIO 枚举成功后总线被无条件断电 ✅ 已修

**现象**：WiFi 驱动接手后，**第一条 CMD52 就超时**，随后 enable function、设块大小全部失败，`wifi_open fail, ret=-1`；上层 `GetWiFiInitStat->>0` 刷屏。

**证据**（`test_log/1.txt`）：
```
I/SDIO: init_sdio ret=0                     ← 枚举成功
clock 0Hz busmode 1 powermode 0 ... Vdd 0   ← 紧接着总线被断电、时钟停到 0
...
E/drv.sdhci: wait 52 completed timeout 0x00000000, arg 0x00000800
```
`0x00000000` 是控制器中断状态原值：**一位都没置** → 控制器根本没把命令发出去（时钟已停）。

**根因**：`rtos/rtthread/components/drivers/sdio/mmcsd_core.c` 的 SDIO 探测分支，把 `mmcsd_power_off(host)` 写成了**无条件执行**（SD 卡 / eMMC 分支都是"仅在初始化失败时"才断电）。

**修改**（当前代码 `mmcsd_core.c:668-674`）：
```c
err = sdio_io_send_op_cond(host, 0, &ocr);
if (!err)
{
    rt_int32_t ret = init_sdio(host, ocr);
    LOG_I("init_sdio ret=%d", ret);
    if (ret)                      /* ← 只在失败时断电 */
        mmcsd_power_off(host);
}
```
> 说明：这一处不在 WiFi 驱动目录内（在 RT-Thread 驱动核心里）。它虽然是"上一版提交顺手改坏"的，但**任何在探测线程之外访问总线的驱动都会踩**，因此保留此修改。

**验证**：`test_log/2.txt` 起，`init_sdio ret=0` 之后**不再出现断电行**，所有 CMD52 正常返回。

### P2 —— WiFi 初始化线程栈太小，触发 HardFault ✅ 已修

**现象**：P1 修好后，驱动一路跑到 fhost 平台初始化收尾（建完 `aicwf_sdio_rx / cli_cmd / fhost_cntrl / fhost_rx / rwnx_timer` 任务），随即 **HardFault**；故障处理函数打印时又撞 ulog 断言（见 P3），日志表现为 `[ULOG-REENT]` + `Assertion failed at function:output_lock`。

**证据**（`test_log/2.txt` / `3.txt` 线程表，两次运行地址完全一致）：
```
aicwf_wi  31  ready   0x20023ba8 0x20023cb0 0x00000400    92%
```
- `aicwf_wi` = `aicwf_wifi_init_task`（线程名被截断到 8 字符），线程栈 **0x400 = 1024 B**；
- `max used 92%` = 最深只到过距栈底 **82 字节**处（该百分比由栈底填充图案反推）；
- 故障点紧跟 `rwnx_timer_task` 创建之后 —— 再深一层调用就踩出栈外。

**根因**：`RWNX_WIFI_STACK_SIZE` 给这个线程只留了 1024 B；AIC 参考实现是 FreeRTOS（`xTaskCreate` 栈单位是**字**），本 port 直接把宏当**字节**用（`platform/rtos/rtos_rtt.c` 的 `aicwf_rtos_task_create_only()` → `rt_thread_create(..., stack_depth, ...)`）。厂商适配文档也把"栈单位换算 / 栈宏过小 → 运行时跑飞"列为已知坑。

**修改**（当前代码 `port/inc/plat_port.h:104`）：
```c
#define RWNX_WIFI_STACK_SIZE        (4096)   /* 原 1024 */
```
其余任务实测余量充足（cli_cmd 60% / fhost_rx 31% / rwnx_timer 18%），未动。

**验证**：`test_log/4.txt`、`5.txt`、`6.txt` 均**运行 40~90 秒无任何死机**。

### P3 —— 第一次 HardFault 的现场被 ulog 重入断言吞掉 ✅ 已加观测（不改核心）

**现象**：HardFault 发生后，日志只有 `[ULOG-REENT]` + `Assertion failed at function:output_lock, line number:297`，**看不到 `hard fault on thread: xxx` 和寄存器**。

**根因**（两条代码事实）：
- 故障处理函数**自己的打印也走 ulog**，而此时被中断的线程正持有 ulog 输出锁 → 异常处理函数（未调用 `rt_interrupt_enter()`，`nest==0`）把锁**递归拿到 hold==2** → 撞上 `RT_ASSERT(ulog.output_locker.hold == 1)`（`ulog.c:297`）。
- 我们的取证打印中 `vectactive=3`（读 `0xE000ED04`）= **已经在 HardFault 里**，进一步说明"先故障、后断言"。

**修改**（不触碰 ulog / cpuport，只在 WiFi 驱动注册钩子）：
- `platform/platform_init.c:85` 新增 `aicwf_fault_hook()`：读 SCB 的 `CFSR/HFSR/MMFAR/BFAR/ICSR` + 硬件压栈异常帧 `r0-r3/r12/lr/pc/psr`，**用 `rt_device_write()` 直写控制台绕开 ulog**，然后返回非 `RT_EOK` 保持核心原有行为；
- `platform_init.c:145` 在 `aic_platform_init()` 里 `rt_hw_exception_install(aicwf_fault_hook)`。

依据：`rtos/rtthread/libcpu/arm/cortex-m33/cpuport.c:475-481` —— 钩子在核心故障打印**之前**被调用，返回 `RT_EOK` 可跳过后续打印；异常帧布局见同文件 `:47-57`。

**效果**：P2 修好后未再出现故障；该钩子作为"保险丝"保留，下次再炸会直接吐出第一次故障的现场（`[AIC-FAULT] ...`）。

### P4 —— SDIO 匹配链的脆弱点 ✅ 已加固 + 已打点

**背景结论（已用仪器证实）**：本次问题的**寻卡与匹配全部成功**，与"厂商 ID 不同导致不注册"无关：
```
I/SDIO: card registered: man=0xc8a1 prod=0x9082 f1prod=0x0000 funcs=1
I/SDIO: init_sdio ret=0
[AIC][SDIO][sdio-match] probe: man=0xC8A1 prod=0x9082 funcs=1 cccr_ver=4
[AIC][SDIO][sdio-match] driver id table first entry: VID=0xC8A1 PID=0xFFFF (ANY=0xFFFF)
[AIC][SDIO]====>aicwf_sdio_drv_register():ret:0
```
> `f1prod=0x0000` 是正常现象：function 1 的 CIS 里只有 `CISTPL_FUNCE(0x21)`、没有 `CISTPL_MANFID(0x20)`，所以 `func->product` 恒为 0，**不能用它判型号**。

**但这段代码有 4 个真实脆弱点**，已加固：

| 脆弱点 | 依据（代码） | 加固 |
| --- | --- | --- |
| core 的匹配**只读 ID 表第一条**，表里第 2 条起永远不生效 | `drivers/include/drivers/sdio.h:151`（`id` 是单指针）；`drivers/sdio/sdio.c:1328-1356`（只访问 `id->manufacturer/product`，`product==ANY` 立即返回） | 在 ID 表上方写死"硬约定"，并把 `[sdio-match]` 打印出来（`sdio_port.c:155-196`, `:338`） |
| 若型号宏都没定义，`aic_sdio_ids[]` 变成**空数组** → 匹配读到边界外 → 偶发"不注册" | `sdio_port.c` 原 `#if/#elif` 链无 `#else` | 加 `#error`（`sdio_port.c:196`），把运行时随机行为变成编译期必现 |
| core 在 product 非 ANY 时会访问 `card->sdio_function[num]->product`，**无 NULL 检查** | `sdio.c:1345-1353` | 表第一条保持 `ANY_PROD_ID`（注释里写死这条约定），另在 probe 内加 NULL 防御（`sdio_port.c:267`） |
| 注册返回值不检查/不重试 | `sdio.c:1395-1404`（`sdio_cards` 为空则返回 `-RT_EEMPTY`）；`sdio_register_driver()` **每次调用都会插一个新节点**（`sdio.c:1393`），所以**不能**循环重试 | `aicwf_sdio_drv_register()` 加返回值检查与定位指引（`sdio_port.c:331-352`），并在注释中写明"禁止循环重试"的理由 |

### P5 —— 编译宏缺 `CONFIG_AIC8800D80N`，D80N 固件/patch 未编入 ✅ 已修（但**不是本次卡点原因**）

**根因**：运行期 chipmatch 判定 `chipid=4 = PRODUCT_ID_AIC8800D80N`，但 `SConscript` 只定义了 `CONFIG_AIC8800D80`。于是：
- `platform/fmac/aic_fw_port.c:94-100` 的 D80N **固件数组包含块不成立** → patch/patch_tbl/cinit/calib 未编入；
- `aic_fw_port.c:1504-1520` 的 D80N 分支**函数体被编译掉** → `size` 保持 0、`*fw_buf` 未赋值 → 取固件"静默失败"。

**证据**（镜像符号，修前 vs 修后）：
```
修前: 只有 fmacfwbt_8800d80_u02 (331 KB)
修后: fmacfwbt_8800d80_u02 0x51038 / fmacfw_patch_8800d80n_u02 0x5c80
      fmacfw_cinit_8800d80n_u02 0x4284 / fmacfw_patch_tbl_8800d80n_u02 0x300
      fmacfw_calib_8800d80n_u02 0x7368            (合计新增 ≈71 KB)
```

**修改**：`SConscript:64` 增加 `'CONFIG_AIC8800D80N'`（**必须与 `CONFIG_AIC8800D80` 并存**：D80N 的主 FMAC 复用 D80 数组，见 `aic_fw_port.c:1516` 注释）。

**副作用**：镜像超出 ROM 分区 19,716 B。按工程侧处理——本 demo 的 `proj.conf` 关闭 **iperf** 与 **lwIP debug**（都在工程配置里，随时可开回），编译通过；当前镜像 1,568,488 B，距 ROM 上限仅剩 ~4.4 KB。

> ⚠️ **重要**：加上 D80N 后现象**完全没变**（仍然 0 次 CMD53）。因此 P5 是**真实缺陷但不是本次卡点的原因**——留着有益（否则将来真走到取固件那步也会失败），但不能解释 P6。

### P6 —— 【未解】固件从未下载，卡在芯片 bootrom 消息通道 ❌

**现象**：SDIO 配置全部完成后，驱动陷入轮询：反复读 **function 1 的寄存器 `0x03`**（= V3 寄存器映射中的 `FLOW_CTRL_Q1`，即"消息流控额度"），读到**恒为 0**，重试 11 轮后打印 `tx msg fc retry fail` 放弃；上层 `GetWiFiInitStat()` 永远为 0。

**为什么这条链能对上**（D40 完整源码可作参考）：
- `aic8800d40/fdrv/macif/rwnx_main.c:885-944` 的 `rwnx_fdrv_init()` 顺序是：
  `"rwnx_fdrv_init enter"` → `rwnx_apm_staloss_init()` → **`system_config_8800d80*()`（靠"消息"给芯片写寄存器）** → `rwnx_platform_on()`（**固件 CINIT/patch/fmac 上传 = CMD53**）→ `start_from_bootrom()`；
- 我们的日志停在 `apm_task`（= `rwnx_apm_staloss_init`）之后、`system_config` 的第一步"发消息"上；库里 `====> D80N stage1: CINIT (bootrom)`、`upload CINIT fw`、`Start app` 等打印**一条都没出现**。

**主机侧已逐条验证正确**（`test_log/6.txt`，把 `demo start` 之后**全部** CMD52 还原并解码）：

| # | 访问 | 含义 | 归属 |
| --- | --- | --- | --- |
| 1-3 | R fn0 `0x02` / R fn0 `0x03` / W fn0 `0x02`←`0x02` | CCCR I/O Enable/Ready、使能 func1 | RT-Thread 核心 |
| 4-6 | R/W fn0 `0x04` ← `0x00` → `0x03` | CCCR 中断使能（先关后开 master+func1） | 核心 / 驱动 |
| 7 | W fn0 `0xF2` ← `0x7F` | AIC 专有 "set fn0 0xF2" | **port** |
| 8-9 | R/W fn0 `0x110/0x111` ← `0x00/0x02` | FBR1 块大小 = **512 B**（设完回读校验） | **port** |
| 10 | W fn1 `0x00` ← `0x07` | `INTR_ENABLE`（V3 映射 0x00） | **port** |
| 11 | W fn1 `0x07` ← `0x01` | `BYTEMODE_ENABLE`（V3 映射 0x07） | **port** |
| 12 | R fn1 `0x03` ×**556** | `FLOW_CTRL_Q1` — **恒为 0** | host 库（等额度） |

对照 D40 参考实现（`aic8800d40/fdrv/layer_common/src/sdio_co.c:51-78` 的 V3 寄存器映射、`platform/hal/sdio_port.c:692-790` 的 V3 初始化、`sdio_def.h:35-45` 的地址常量）：**主机侧没有遗漏、没有错写**（`INTR_ENABLE=0x00`、`FLOW_CTRL_Q1=0x03`、`BYTEMODE_ENABLE=0x07` 全部匹配；D40 里那两处差异代码本身也是 `#if 0` 关掉的）。

**本轮新增的轨迹打印结论**（`test_log/6.txt`）：
- `[trace] load_firmware / load_patch_tbl / load_calib` → **0 次**（库从没来取固件）
- `[trace] CMD53 ...` → **0 次**（一个字节都没搬；连"发一条消息"都没发出去）
- 全日志只有 2 条 trace（都是初始化末尾的寄存器写）

**结论**：主机侧已经把该做的全做完；**芯片侧（bootrom）在 50 秒内 556 次都没有发放消息额度**。这已经不是我们这层代码能解释/修复的范围。

**最可能的原因（按可能性排序，待外部确认）**：
1. 芯片的 CPU/bootrom 没有真正运行（SDIO PHY 是硬件，仍然能完成枚举）——例如模组还有未释放的复位脚、启动模式 strap 不对、或供电模式（DCDC/LDO）与该模组不符；
2. bootrom 需要主机**先做一步我们没做的握手**（某个寄存器/唤醒序列），主机库版本与芯片 bootrom 版本不匹配；
3. 模组自带 flash 且已烧固件，芯片启动路径与"主机下载固件"模式不同；
4. 预编译库版本（`NV1.1.6 ... 20260915`）对 PID `0x9082`（D80LN）的 bootrom 流程支持不完整。

### 3.2 给硬件 / 模组

1. 本板只驱动了 **GPIO124（`AIC_WIRELESS_PWR_GPIO=124`）** 作为芯片电源脚。模组是否还有 **RESET_N / CHIP_EN / WAKEUP / 启动模式 strap** 需要特定电平？
2. 模组的供电模式是 **DCDC 还是 LDO**？（厂商文档提到 `aicwifi_vrf_mode = VRF_DCDC_MODE`，配错可能导致数字核不启动而 SDIO PHY 仍工作。）
3. 模组上是否**自带 flash 且已烧固件**？若有，芯片的启动路径与"主机通过 SDIO 下载固件"是否冲突？
4. 芯片电源时序是否满足手册（我们当前：拉低 10 ms → 拉高 → 等 200 ms，之后才开始 SDIO 枚举）。

## 6. 附录 B：术语速查

| 术语 | 一句话解释 |
| --- | --- |
| **CMD0/5/3/7** | 寻卡四步：复位 → 问"是 SDIO 卡吗、几个功能" → 发短地址 RCA → 选中该卡 |
| **CMD52 / CMD53** | 单字节寄存器读写 / 块传输。**固件下载必然走 CMD53** |
| **CCCR** | 卡级公共控制寄存器（如 `0x02` I/O Enable、`0x04` 中断使能） |
| **FBR** | 每个 function 的寄存器块（func1 从 `0x100` 起，`0x110/0x111` 是块大小） |
| **CIS** | 卡的"身份证+能力表"；`0x20`=厂商/产品 ID，`0x21`=功能信息 |
| **func0 / func1** | func0 管公共控制；func1 是 WiFi 数据/消息通道 |
| **流控 / msg fc** | 主机给芯片发消息前要拿到的"额度"；D80 系在 func1 偏移 `0x03`，由芯片侧写入 |
| **bootrom / CINIT / patch / fmac** | 芯片内置引导程序 / 分阶段加载的三类固件镜像 |
| **HardFault** | Cortex-M 的硬件异常；现场看 `CFSR/HFSR/BFAR/PC/LR` |
| **ulog 重入** | 线程持锁打日志时又被异常打断，异常处理再打日志 → 递归持锁触发断言 |
